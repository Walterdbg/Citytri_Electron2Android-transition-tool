[DEFECT-002 — see Defects section]
Time: shortly after [012]
Area / feature: App responsiveness — group interactions
Request or objective: User reported the app freezing/not responding when opening or setting Primary on a record inside a specific email group.
Action taken: User A/B tested against the previous exe build — confirmed the freeze does NOT happen there, isolating the cause to the color-palette change in [DEFECT-001]/[012]. Root cause found: `groupColor()` filtered the full record list, and for each record in that filter called `emailGroupSize()`, which itself re-filtered the full list again — an O(n^2) cost per call to a function invoked ~3x per row.
Files modified: renderer/index.html — added `getGroupIndex()`/`getGroupColorMap()`, computing an email->count Map and email->color Map exactly once per render (cache invalidated at the top of `render()`), instead of recomputing per row.
Verification performed: Direct benchmark simulating a 411-record/15-group dataset — old implementation 1156ms per render, new implementation 1ms per render.
Result: PASS (fix verified by benchmark; not yet re-confirmed live by Walter in the running app as of this log entry)
Observed issue: Real, severe regression — full app freeze, confirmed root cause and fix.
Follow-up required: Walter to confirm live in the rebuilt exe.
Roadmap update required: YES — new standing rule needed (see Decisions/Documents below).
